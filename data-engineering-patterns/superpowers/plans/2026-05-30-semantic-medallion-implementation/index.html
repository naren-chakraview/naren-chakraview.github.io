    Semantic Medallion Implementation Plan¶

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: Implement three semantic medallion pattern extensions (Semantic CDC, Semantic Batch Lakehouse, Semantic Federated Query) plus enterprise-modernization case study integration, enabling RDF-based data unification across polyglot sources.

    Architecture: Three patterns work together: Semantic CDC mints IRIs and deduplicates entities at ingest time; Semantic Batch Lakehouse converts Silver tables to RDF triples; Semantic Federated Query unifies SQL and SPARQL queries via a shared ontology. All patterns use Apache Jena TDB2 as the semantic store, with Iceberg as the analytical store.

    Tech Stack: - Semantic CDC: Python 3.11, Debezium 2.x, Kafka 3.x - Semantic Batch Lakehouse: Scala 2.12, Spark 3.5, Apache Jena 4.x, Iceberg 1.5 - Semantic Federated Query: Trino 450, Jena SPARQL endpoint - Testing: pytest (Python), scalatest (Scala), docker-compose (local dev)

    import hashlib
from typing import Dict, Any, Optional


class IRIResolver:
    """Deterministic IRI (Internationalized Resource Identifier) minting for entities"""

    def __init__(self, base_iri: str = "https://company.com"):
        self.base_iri = base_iri

    def mint_iri(
        self, 
        entity_type: str, 
        entity_dict: Dict[str, Any],
        key_fields: Optional[list] = None
    ) -> str:
        """
        Mint a stable IRI for an entity.

        Args:
            entity_type: "customer", "invoice", "order", etc.
            entity_dict: entity properties
            key_fields: fields to use for deduplication (default: all fields)

        Returns:
            Stable IRI: "https://company.com/{entity_type}#{hash}"
        """
        if key_fields is None:
            key_fields = sorted(entity_dict.keys())

        # Normalize key values
        key_parts = []
        for field in key_fields:
            if field in entity_dict:
                value = str(entity_dict[field]).lower().strip()
                key_parts.append(value)

        # Create deterministic hash
        key_string = "|".join(key_parts)
        hash_value = hashlib.sha256(key_string.encode()).hexdigest()[:16]

        return f"{self.base_iri}/{entity_type}#{hash_value}"

    def normalize_email_domain(self, email: str) -> str:
        """Normalize email for deduplication"""
        return email.lower().strip()

class IRIMinterService:
    """Kafka consumer that enriches CDC records with IRIs"""

    def __init__(self, config: Dict[str, Any]):
        self.config = config
        self.resolver = IRIResolver(base_iri=config.get("base_iri", "https://company.com"))
        self.entity_rules = config.get("entity_rules", {})

    def enrich_record(self, entity_type: str, record: Dict[str, Any]) -> Dict[str, Any]:
        """Add IRI to a record based on entity resolution rules"""

        # Get entity-specific rules
        rules = self.entity_rules.get(entity_type, {})
        key_fields = rules.get("key_fields", list(record.keys()))

        # Mint IRI
        iri = self.resolver.mint_iri(entity_type, record, key_fields=key_fields)

        # Return enriched record
        enriched = record.copy()
        enriched["iri"] = iri
        enriched["_entity_type"] = entity_type
        enriched["_iri_minted_at"] = self._now_iso()

        return enriched

    def process_kafka_record(self, kafka_record: Dict[str, Any]) -> Optional[Dict[str, Any]]:
        """Process a Kafka record from Debezium CDC"""

        try:
            # Parse Debezium message
            payload = kafka_record.get("value", {})
            if not payload:
                return None

            # Determine entity type from topic
            topic = kafka_record.get("topic", "")
            entity_type = self._topic_to_entity_type(topic)

            if not entity_type:
                logger.warning(f"Could not determine entity type from topic: {topic}")
                return None

            # Extract after-image (new state)
            after = payload.get("after", {})
            if not after:
                return None

            # Enrich with IRI
            enriched = self.enrich_record(entity_type, after)
            enriched["_source_topic"] = topic
            enriched["_kafka_key"] = kafka_record.get("key")

            return enriched

        except Exception as e:
            logger.error(f"Error processing Kafka record: {e}")
            return None

    def _topic_to_entity_type(self, topic: str) -> Optional[str]:
        """Map Kafka topic to entity type"""
        # Example: "postgres.public.customers" -> "customer"
        # "salesforce.accounts" -> "customer"

        topic_lower = topic.lower()
        if "customer" in topic_lower or "account" in topic_lower:
            return "customer"
        elif "invoice" in topic_lower:
            return "invoice"
        elif "transaction" in topic_lower:
            return "transaction"
        elif "order" in topic_lower:
            return "order"

        return None

    def _now_iso(self) -> str:
        """Return current timestamp in ISO format"""
        from datetime import datetime, timezone
        return datetime.now(timezone.utc).isoformat()

    from typing import Dict, Any, List, Optional


class EntityResolver:
    """Entity resolution and deduplication logic"""

    def __init__(self, rules: Dict[str, Any]):
        """
        Initialize with deduplication rules

        Args:
            rules: dict mapping entity_type -> {match_fields, normalize_fn}
        """
        self.rules = rules

    def deduplicate(
        self, 
        entity_type: str, 
        record: Dict[str, Any],
        existing_records: List[Dict[str, Any]]
    ) -> Optional[str]:
        """
        Check if record matches an existing entity

        Returns:
            Existing entity IRI if match found, None otherwise
        """

        rules = self.rules.get(entity_type, {})
        match_fields = rules.get("match_fields", [])

        if not match_fields:
            return None

        # Normalize current record
        current_key = self._normalize_key(record, match_fields)

        # Check against existing records
        for existing in existing_records:
            existing_key = self._normalize_key(existing, match_fields)
            if current_key == existing_key:
                return existing.get("iri")

        return None

    def _normalize_key(self, record: Dict[str, Any], fields: List[str]) -> str:
        """Create normalized key for comparison"""
        parts = []
        for field in fields:
            value = record.get(field, "")
            if isinstance(value, str):
                value = value.lower().strip()
            parts.append(str(value))
        return "|".join(parts)


class DeduplicationCache:
    """In-memory cache for deduplication across Kafka topics"""

    def __init__(self, max_size: int = 10000):
        self.cache = {}  # entity_type -> {normalized_key -> iri}
        self.max_size = max_size

    def get_iri(self, entity_type: str, key: str) -> Optional[str]:
        """Retrieve cached IRI for entity"""
        return self.cache.get(entity_type, {}).get(key)

    def put_iri(self, entity_type: str, key: str, iri: str):
        """Cache IRI for entity"""
        if entity_type not in self.cache:
            self.cache[entity_type] = {}

        if len(self.cache[entity_type]) >= self.max_size:
            # Simple eviction: remove oldest (in production, use LRU)
            oldest_key = next(iter(self.cache[entity_type]))
            del self.cache[entity_type][oldest_key]

        self.cache[entity_type][key] = iri

    package io.chakraview.semantic

import org.apache.jena.rdf.model._
import org.apache.jena.vocabulary.RDF
import scala.collection.JavaConverters._


class SemanticTransformer(config: RDFConfig) {

  private val model = ModelFactory.createDefaultModel()
  private val baseIRI = config.baseIRI
  private val ontologyNS = s"$baseIRI/ontology#"

  /**
   * Convert a record to RDF triples
   */
  def recordToRDFTriples(
    entityType: String,
    record: Map[String, String]
  ): List[String] = {

    val iri = record.get("iri").getOrElse(
      throw new IllegalArgumentException(s"Record missing 'iri' field: $record")
    )

    val triples = scala.collection.mutable.ListBuffer[String]()

    // Type triple
    triples += s"<$iri> a :${capitalize(entityType)} ."

    // Property triples
    record.foreach { case (key, value) =>
      if (key != "iri" && !key.startsWith("_")) {
        val predicate = camelCase(key)
        val escapedValue = escapeRDFLiteral(value)
        triples += s"<$iri> :$predicate $escapedValue ."
      }
    }

    triples.toList
  }

  /**
   * Create reference between two IRIs
   */
  def createReference(
    fromIRI: String,
    predicate: String,
    toIRI: String
  ): String = {
    s"<$fromIRI> :$predicate <$toIRI> ."
  }

  private def capitalize(s: String): String = 
    s.head.toUpper + s.tail

  private def camelCase(s: String): String = {
    s.split("_").zipWithIndex.map {
      case (part, 0) => part
      case (part, _) => capitalize(part)
    }.mkString
  }

  private def escapeRDFLiteral(value: String): String = {
    val escaped = value
      .replace("\\", "\\\\")
      .replace("\"", "\\\"")
      .replace("\n", "\\n")
    s"\"$escaped\""
  }

  def validateTriple(triple: String): Boolean = {
    // Basic validation: subject, predicate, object, period
    triple.contains("<") && 
    triple.contains(">") && 
    triple.contains(" ") &&
    triple.endsWith(" .")
  }
}

class JenaWriter(config: RDFConfig) {

  private val tdb2Path = config.tdb2Path

  /**
   * Write RDF triples to both Iceberg and Jena TDB2
   */
  def writeRDF(
    triples: Seq[(String, String, String)],  // (subject, predicate, object)
    spark: org.apache.spark.sql.SparkSession
  ): Unit = {

    // Write to Iceberg (Ntriples format)
    writeToIceberg(triples, spark)

    // Write to Jena TDB2
    writeToJenaTDB2(triples)
  }

  private def writeToIceberg(
    triples: Seq[(String, String, String)],
    spark: org.apache.spark.sql.SparkSession
  ): Unit = {
    import spark.implicits._

    val df = spark.createDataFrame(triples).toDF("subject", "predicate", "object")

    df.write
      .mode(SaveMode.Append)
      .format("iceberg")
      .option("write-format", "parquet")
      .saveAsTable(icebergTable)

    println(s"Wrote ${triples.length} triples to Iceberg table: $icebergTable")
  }

  private def writeToJenaTDB2(
    triples: Seq[(String, String, String)]
  ): Unit = {

    val dataset = TDB2Factory.connectDataset(tdb2Path)
    val model = dataset.getDefaultModel

    val vf = ModelFactory.createDefaultModel().getResource("")

    triples.foreach { case (subject, predicate, `object`) =>
      val s = model.createResource(subject)
      val p = model.createProperty(predicate)
      val o = model.createResource(`object`)

      model.add(s, p, o)
    }

    dataset.commit()
    dataset.close()

    println(s"Wrote ${triples.length} triples to Jena TDB2: $tdb2Path")

import scala.util.{Try, Success, Failure}

  def main(args: Array[String]): Unit = {

    // Load config
    val config = RDFConfig.fromEnv()

    // Validate config
    RDFConfig.validate(config) match {
      case Failure(e) => 
        System.err.println(s"Invalid configuration: ${e.getMessage}")
        System.exit(1)
      case Success(_) => ()
    }

    // Create Spark session
    val spark = SparkSession
      .builder()
      .appName("semantic-batch-lakehouse")
      .config("spark.sql.catalog.lakehouse", "org.apache.iceberg.spark.SparkCatalog")
      .config("spark.sql.catalog.lakehouse.type", "rest")
      .config("spark.sql.catalog.lakehouse.uri", config.icebergRestURI)
      .getOrCreate()

    try {
      val transformer = new SemanticTransformer(config)
      val writer = new JenaWriter(config)

      // Read Silver tables
      val silveTables = config.icebergSilverTables
      for (tableName <- silveTables) {
        val silverDF = spark.table(s"${config.icebergSilverDatabase}.$tableName")
        processTable(tableName, silverDF, transformer, writer, spark)
      }

      println("Semantic Batch Lakehouse job completed successfully")
    } catch {
      case e: Exception =>
        System.err.println(s"Error running semantic batch lakehouse: ${e.getMessage}")
        e.printStackTrace()
        System.exit(1)
    } finally {
      spark.stop()
    }
  }

  private def processTable(
    tableName: String,
    df: DataFrame,
    transformer: SemanticTransformer,
    writer: JenaWriter,
    spark: SparkSession
  ): Unit = {

    println(s"Processing table: $tableName")

    val records = df.collect()

    val triples = scala.collection.mutable.ListBuffer[(String, String, String)]()

    for (row <- records) {
      val record = row.getValuesMap[String](row.schema.fieldNames)
      val rdfTriples = transformer.recordToRDFTriples(tableName.stripSuffix("s"), record)

      // Parse triples into (subject, predicate, object) tuples
      // Simple parser: "<s> <p> <o> ."
      for (tripleStr <- rdfTriples) {
        val parts = tripleStr.split(" ")
        if (parts.length >= 4) {
          val subject = parts(0)
          val predicate = parts(1)
          val `object` = parts.slice(2, parts.length - 1).mkString(" ")
          triples += ((subject, predicate, `object`))
        }
      }
    }

    writer.writeRDF(triples, spark)
    println(s"Wrote ${triples.length} triples from table: $tableName")
  }

    # Phase 2: Semantic Unification - Case Study Scenario

## Background

The company has completed Phase 1 modernization:
- Migrated from Java EE monolith to cloud-native microservices
- Implemented traditional medallion architecture (Bronze → Silver → Gold)
- Operational analytics working via Trino on Iceberg tables
- BI dashboards running on dimensional (Kimball) model

## The Problem

After Phase 1, the analytics team encounters a new challenge:

**Business Question:** "Which customers are at high churn risk?"

**Data Sources:**
- Shopify (storefront) - customer purchase history
- Salesforce (support) - support tickets, escalations
- Stripe (payments) - payment failures, disputes
- Custom Postgres (orders) - internal order system

**Current Approach (Manual):**
1. Extract customer from Shopify: ID = `shop_cust_123`
2. Find same customer in Salesforce: ID = `0011234567`
3. Find same customer in Stripe: ID = `cus_xyz`
4. Write custom SQL joins across 4 tables
5. Manually track deduplication rules
6. Every analyst writes slightly different joining logic

**Problems:**
- Entity resolution logic scattered across dashboards
- No single source of truth for "who is this customer?"
- Adding new data source (e.g., HubSpot) requires schema renegotiation
- Audit trail unclear: which system owns which facts?

## Phase 2 Solution

**Apply semantic medallion patterns:**

1. **Semantic CDC** — mint stable IRIs for customers from all sources
   - "shop_cust_123" + "0011234567" + "cus_xyz" → same IRI
   - Kafka enriches records with IRI before Silver layer

2. **Semantic Batch Lakehouse** — convert Silver tables to RDF
   - "Shopify customer 123 purchased order X"
   - "Salesforce ticket Y belongs to customer Z"
   - Data becomes self-describing

3. **Semantic Federated Query** — SPARQL queries on unified view
   - **Query:** "Customers with 3+ support escalations AND payment failures in last 30 days"
   - **One SPARQL query**, no manual joins, no entity resolution logic

## Outcomes

✅ **Single source of truth:** Customers are identified by stable IRI across all systems
✅ **Self-service analytics:** Analysts write SPARQL, not custom SQL joins
✅ **Audit trail:** RDF triples show "fact X came from system Y at time Z"
✅ **Easy to add sources:** New data source (HubSpot) wired to existing ontology in days
✅ **Coexistence:** Phase 1 dimensional model untouched; Phase 2 semantic layer works alongside

SELECT ?customer ?customerName (COUNT(?ticket) as ?ticketCount) (COUNT(?failure) as ?failureCount)
WHERE {
  ?customer a :Customer .
  ?customer :hasName ?customerName .
  ?customer :hasStatus :Active .

  # High-priority support tickets in last 30 days
  OPTIONAL {
    ?customer :hasTicket ?ticket .
    ?ticket :ticketPriority :High .
    ?ticket :ticketCreatedAt ?ticketDate .

  OPTIONAL {
    ?customer :hasPaymentEvent ?failure .
    ?failure :paymentType :Failed .
    ?failure :paymentDate ?failureDate .
    FILTER (?failureDate > NOW() - P30D)

}
GROUP BY ?customer ?customerName
HAVING ((COUNT(?ticket) >= 3) OR (COUNT(?failure) >= 2))

    # Semantic Medallion Architecture

> **What it is:** An evolution of the traditional Bronze-Silver-Gold medallion pattern that embeds knowledge graph structure into the data itself via RDF triples, enabling entity unification, semantic reasoning, and ontology-driven querying.

## The Three Patterns

### [Semantic CDC](../cdc-pipeline/variants/debezium-kafka-semantic/) — Entity Resolution at Ingest

**Problem:** Same customer appears as different IDs in Salesforce, Stripe, Postgres.

**Solution:** Mint stable IRIs (Internationalized Resource Identifiers) for each entity at CDC ingest time, performing deterministic deduplication based on configurable rules.

**Stack:** Debezium, Kafka, IRI Minter Service (Python), entity resolver

---

### [Semantic Batch Lakehouse](../batch-lakehouse/variants/spark-iceberg-semantic/) — RDF Generation

**Problem:** Silver tables are relational; relationships aren't explicit. Every query requires JOINs.

**Solution:** Convert Silver tables to RDF triples, outputting to both Iceberg (analytical) and Jena TDB2 (semantic store). Relationships become first-class citizens in the data.

**Stack:** Spark, Iceberg, Apache Jena, Jena TDB2

---

### [Semantic Federated Query](../federated-query/variants/trino-jena-sparql/) — Multi-Source SPARQL

**Problem:** Entity resolution and schema negotiation is manual and repetitive.

**Solution:** Define a shared ontology. Query it via SPARQL (for semantic reasoning) or SQL (for analytics). One unified view, multiple query languages.

**Stack:** Trino, Jena TDB2, SPARQL endpoint

---

## Data Flow: Bronze → Silver → RDF Gold
    Salesforce + Stripe + Postgres ↓ Semantic CDC (IRI Minting) ↓ Silver (tables + IRIs) ↓ Semantic Batch Lakehouse (RDF generation) ↓ ┌─────────────────────────┐ │ Iceberg (Ntriples) │ Analytical queries (SQL via Trino) │ Jena TDB2 (RDF store) │ Semantic queries (SPARQL) └─────────────────────────┘ 
    ---

## When to Use

**Use semantic medallion when:**
- You have polyglot data sources (multiple systems of record)
- Entity resolution is a bottleneck (customers in 5 different systems)
- You want semantic reasoning (ontology-driven inference rules)
- You need audit trails (what system owns which facts?)
- You want self-describing data (ontology AS the catalog)

**Start with traditional medallion if:**
- Single source of truth (no deduplication needed)
- Analytical queries are simple (few JOINs)
- Team is unfamiliar with RDF/SPARQL

**Coexist with Phase 1:**
- Dimensional model (Kimball) works great for analytics
- Semantic layer handles entity unification
- Both can serve same underlying data

## Comparison: Traditional vs. Semantic

### Traditional Medallion
- **Query pattern:** SQL JOINs across tables
- **Entity resolution:** Per-query (manual)
- **Catalog:** Separate from data (metadata tool)
- **Reasoning:** None (business rules in code)

    # ADR-0011: Semantic Medallion Architecture Approach

**Date:** 2026-05-30  
**Status:** Accepted

## Problem

Traditional medallion architecture (Bronze-Silver-Gold) handles data transformation well but struggles with entity unification across polyglot sources. Entity resolution logic is scattered across queries, dashboards, and pipelines. Adding new data sources requires schema renegotiation.

## Decision

Extend the medallion pattern with semantic (RDF/knowledge graph) capabilities:

1. **Semantic CDC:** Mint stable IRIs for entities at ingest time, enabling deterministic deduplication
2. **Semantic Batch Lakehouse:** Convert Silver tables to RDF triples for explicit relationship representation
3. **Semantic Federated Query:** Query via SPARQL (semantic) or SQL (analytics) on unified ontology

## Rationale

- **Single source of truth:** One IRI per entity across all sources (vs. manual joins)
- **Self-service analytics:** SPARQL queries on ontology (vs. custom SQL per use case)
- **Audit trail:** RDF triples show fact provenance (vs. lost in SQL joins)
- **Extensible:** New data sources map to existing ontology (vs. schema migration)
- **Coexistent:** Semantic layer works alongside Phase 1 dimensional model (no disruption)

## Consequences

- ✅ Unified entity view, reduced query complexity
- ✅ Audit trail for compliance
- ✅ Easy onboarding of new sources
- ⚠️ Operational overhead: IRI minting rules, ontology maintenance
- ⚠️ Learning curve: SPARQL not native to SQL teams
- ⚠️ Storage overhead: dual storage (Iceberg + Jena TDB2)

## Alternative Considered

1. **Enhanced SQL with window functions:** Simpler but doesn't solve schema negotiation
2. **Master data management (MDM) tool:** Heavier operational burden, slower to deploy
3. **Semantic as separate system:** Works but no integration with analytics (two catalogs)

Semantic medallion chosen because it unifies concerns (entity resolution + analytics) and coexists with Phase 1.

    # ADR-0012: RDF Storage and Apache Jena Choice

**Date:** 2026-05-30  
**Status:** Accepted

## Problem

Need to choose RDF storage backend and triple store for semantic medallion. Options include Apache Jena, RDF4J, GraphDB (commercial), Virtuoso, Blazegraph.

## Decision

**Dual storage approach:**
- **Iceberg (Ntriples):** Analytical queries via SQL, schema-on-read
- **Apache Jena TDB2:** Semantic queries via SPARQL, ontology-aware

**Rationale for Jena:**
- Open source (no licensing)
- Mature (20+ years production use)
- Good SPARQL engine with reasoning support
- Self-hosted (no vendor lock-in)
- Easy docker deployment
- Well-documented

## Rationale for Dual Storage

- **Iceberg:** Familiar to analytics teams (SQL), scales to billions of rows, integrates with Trino
- **Jena TDB2:** Optimized for SPARQL, supports inference, better for semantic queries

Dual storage allows both analytical (SQL) and semantic (SPARQL) query patterns.

## Consequences

- ✅ No vendor lock-in
- ✅ Open source community
- ✅ Both analytical and semantic patterns supported
- ⚠️ Operational complexity: sync Iceberg ↔ Jena TDB2
- ⚠️ Scale limits: Jena TDB2 tested to ~100M triples (upgrade to GraphDB/Virtuoso for higher scale)

## Upgrade Path

If scale exceeds Jena TDB2 capacity:
1. Migrate to GraphDB (enterprise SPARQL engine, 1B+ triples)
2. Or Virtuoso (multi-model, RDF + SQL)
3. Iceberg storage unchanged (format-agnostic)

    # ADR-0013: Entity Resolution Strategy for IRI Minting

**Date:** 2026-05-30  
**Status:** Accepted

## Problem

How to deterministically identify same entity across multiple sources (e.g., customer in Salesforce, Stripe, Postgres) and mint stable IRIs?

## Decision

Deterministic, rule-based entity resolution at CDC ingest time:

1. **Rules per entity type:** Configure matching fields (e.g., email + domain for customers)
2. **Normalization:** Lowercase, trim, hash for deterministic IRI generation
3. **Deduplication cache:** In-memory cache for quick lookup across Kafka topics
4. **IRI format:** `https://company.com/{entity_type}#{hash(normalized_key)}`

## Rationale

- **Deterministic:** Same entity always gets same IRI (reproducible)
- **Simple:** No complex ML or fuzzy matching (MVP)
- **Fast:** Hash-based, no external service dependencies
- **Configurable:** Rules per domain/entity type
- **Auditable:** IRI generation is transparent and reproducible

## Limitations (Accepted)

- ❌ No fuzzy matching (e.g., "Bob Smith" vs "Robert Smith")
- ❌ No multi-step deduplication (e.g., linking via email, then phone)
- ❌ No real-time updates (deterministic, batch-based)

## Future Enhancements

1. **Fuzzy matching:** Add Levenshtein distance for name matching
2. **ML-based dedup:** Use embedding models for complex matching
3. **Real-time updates:** Stream-based entity resolution with Spark Streaming
4. **External resolver:** Call MDM or Cassandra lookup service

For MVP, deterministic rules are sufficient and operationally simple.

## Consequences

- ✅ Simple to implement and understand
- ✅ No external dependencies
- ✅ Reproducible and auditable
- ⚠️ Manual rule definition per domain
- ⚠️ Limited to exact-match scenarios
