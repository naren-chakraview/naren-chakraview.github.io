Federated Governance Is a Trust Problem, Not a Policy Document

My data mesh's access policy was correct, tested and fail-closed. It also believed whatever it was told about who was asking.

By Narendra Loganathan • 15 min read • Updated 2026-11-14

This is the request that broke my confidence in my own governance:

POST /api/access-requests              <- no token, no login required
{
  "user_id":   "anyone@example.com",   <- any name will do
  "user_role": "risk_analyst",         <- typed by the caller, never checked
  "data_product_id": "risk-compliance.risk-scores",
  "action": "read",
  "justification": "testing"
}

200 OK
{"id": "req_1", "status": "approved",  <- no human reviewed it
 "message": "Access granted"}

The risk scores in my reference data mesh are classified sensitive. The access policy says a risk analyst may read sensitive data without a human approving it. The policy is written in Rego, versioned, covered by tests, and fails closed if the policy engine is unreachable. It did exactly what it was written to do.

The problem is the words “risk analyst”. They came from the request body, typed by whoever sent it. Nothing checked them. The policy was evaluating a claim.

In the first article of this series I argued that federated governance breaks at “who” once the consumer is an agent, because nothing in it can say which machine is acting for which person. When I went back to the code to write this article, I found it could not say which person was acting, either. This article is about why, and how I fixed it.

What the industry has right

Start with what is not in dispute. Federated computational governance, the fourth principle of data mesh, has matured from a slogan into a practice. Policy as code is the right move: rules that are versioned, reviewed, tested and evaluated by machines, instead of PDFs that someone reads once. OPA is widely used for it, and OpenCredo and Starburst have both written well about putting it at the heart of a mesh. Thoughtworks’ Looking Glass 2026 puts it plainly: governance “moves from committees to real-time controls and auditability”, and should be treated “as code and product”. The academic side is catching up too: a paper at ICSA 2026 distills 49 industry sources and six practitioner interviews into a framework of eight design decisions and 104 options for building such governance.

All of that work is about the policy. It is good work, and my own mesh followed it. But it mostly takes the policy’s inputs on trust: who is asking, through which software, and by which door. That is not a policy question. It is a trust question, and zero trust has been answering it for workloads for a decade.

The audit: what my governance actually trusted

My fintech mesh has five domains on an Iceberg lakehouse, a discovery portal where consumers request access, OPA for decisions, column masking, and an audit log. A few weeks before this audit, I had fixed its policy: OPA 1.0 with the current Rego syntax, default deny, fail-closed masking, an audit write that blocks the read if it fails. I read it again as a zero-trust reviewer would, asking of every decision “how do you know?” Seven answers were “we don’t”.

The person was a claim. The access-request API took user_id and user_role from the JSON body. Nothing authenticated the caller. That is the request at the top of this article.

The masking never ran. The function that masks columns and writes the audit record was real, tested code. Its only callers were its unit tests. No read path in the repository used it.

An approval went nowhere. When a request needed a human, the approval became a record in memory. Nothing checked it when data was read, it never expired, and a restart erased it.

Every door below the policy was open. Object storage ran with its default credentials. The Iceberg catalog had no authentication. The three domains’ SPARQL endpoints, which I added for the semantic layer in the previous article, accepted queries, updates and graph writes from anyone who could reach them, and served customer names and emails unmasked. The policy guarded a front door in a building with no walls.

The workload was invisible. Every policy input described a person. Nothing identified the software making the request, so the policy could not tell an analyst’s notebook from a nightly batch job from an AI agent acting for that analyst.

Lineage was an empty module. One line, a comment. Nothing recorded which code, which inputs and which workload produced a data product.

“Federated” was one central file. Every product was governed by a single policy file written by the platform team. A domain had nowhere to express rules for its own product.

None of this is exotic. Each is the kind of gap a careful team ships, because each hides behind a component that looks finished. The common cause is the point of this article: I had built governance as a decision service, not as a trust boundary. It answered “should this role see this column?” correctly, and never established who was asking, through which workload, by which door, or about data from where.

The fix: zero-trust primitives at the data product’s boundary

I fixed it in the repository and, as with the semantic drift, kept the before beside the after. The old state is tagged trust-before, the frozen code sits under examples/trust-gaps/before/, and five demos print the before and after. The design has six parts, and none of them is new. They are the primitives from my zero-trust article, applied to data.

Prove both parties. Every request carries two identities, and both are verified. The person presents a signed token from the identity provider; the boundary checks its signature, issuer, audience and expiry, and takes the subject and roles from the verified claims only. The software presents a client certificate with a SPIFFE ID, checked by the gateway against the certificate authority. A request body that still tries to name a role is rejected outright, so an old client fails loudly instead of having its claim silently dropped. The request from the top of this article now gets a 401, and with a valid analyst token it gets a 400: “identity comes from the verified token; remove: user_role”.

One enforcement point per data product, in front of every door. A boundary service is now the only network path to product data, for table reads and for SPARQL alike. Storage, the catalog, the SPARQL servers and the policy engine sit on an internal network with no published ports, and the gateway reaches the boundary over mutual TLS. The SPARQL servers lost their update and graph-write endpoints. Every step fails closed: no token, no certificate, no policy decision or no audit write means no data. And the masking function finally has a caller.

Federated means layered. The platform team owns guardrails that no domain can override: a verified person and workload on every request, approval for personal data, a masking floor, and an audit record. Each domain owns a policy file for each of its products: who may read it, whether reads need approval, and how each column is shown. A read needs both the guardrails and the domain policy to allow it, and the stricter masking wins. The test that convinced me: a domain policy that tries to show personal data in the clear gets overruled by the guardrail, and the audit shows partial masking on every column.

Grants, not approvals. An approval, made by an authenticated product owner, becomes a stored grant scoped to the person, the workload, the product, the columns and the purpose, with an expiry. The boundary checks it at read time and records its id in the audit. Without a grant the read is refused; with one it succeeds; two days later, when it has expired, it is refused again.

Lineage as attestation. When a producer publishes a snapshot, it signs a record in the format the software supply chain already uses (an in-toto statement in a DSSE envelope): the snapshot’s SHA-256 digest, the producing workload’s SPIFFE ID, the code commit and the input snapshots. Each producer has its own key, and the boundary keeps a separate, read-only record of which producer and key each product expects, so whoever can write an attestation cannot also change what verifies it. Every read reports whether the snapshot’s lineage verified. Change one byte of the snapshot and it reports false. A product can go further and declare in its contract that it must not be read without verified lineage, and the guardrail enforces that.

Audit as evidence. Every decision, allowed or denied, records the person, their roles, the workload, the product, the columns, the masking applied, the policy revisions, the grant, the lineage result and, for SPARQL, a hash of the query. “Who saw this, through what, and why was it allowed?” now has a record, not a reconstruction.

The side door was harder than the front door

The SPARQL endpoint is worth its own section, because it taught me the most. Putting it behind the boundary was easy. Making the boundary’s masking hold for an arbitrary query was not, and each review of the fix found another hole.

The first version masked each result by the name of its variable. So a query could read an email and rename it after a harmless column: BIND(?email AS ?amount) came back in the clear to someone granted only amount. The fix was to classify each result by the predicate its value is read from, never by its name, and to refuse the constructs that can compute or rename a value: BIND, expressions in SELECT, aggregates, subqueries and VALUES. The same pass refused SERVICE, which would otherwise have let a query authorized for one product ask its SPARQL server to fetch another domain’s data over the internal network, under the wrong product’s grant.

The second version checked only the predicates behind the columns a query returned. A query could still match on data it could not read, ?c f:amount ?amount ; f:customerEmail "john@acme.com", and the presence of rows answered “does this person have transactions?”. Now every predicate in the query, returned or only matched, must be in the product’s contract and covered by the caller’s grant. A third review found the same test hiding inside FILTER EXISTS, where the check could not see it, so the boundary now refuses EXISTS and NOT EXISTS too.

The lesson generalizes. A query language is a door with a lock that has to understand everything the language can say. If you expose one, either keep it to a small, analyzable subset, as I did, or allow only named, reviewed queries per product. And accept that row counts and timing can still leak a little through any query interface, which is why the audit records a hash of every query.

Where zero-trust-rs fits

The boundary here is a small Python service behind nginx, because the point of the repository is to be read. In production, that role suits a gateway like zero-trust-rs, the Rust reference gateway I built alongside the zero-trust article: mutual TLS between SPIFFE identities, verified tokens, and capability policy checked at every hop against the workload making that hop.

There is one thing this article deliberately leaves out: an agent acting for a person. The policy input already carries the person and the workload separately, so a delegation chain, the record that this agent acted for that analyst through these services, can be added without redesign. That is the subject of the next article.

What it costs

Running an identity plane is real work. In the repository, a development identity provider and certificate authority stand in for a company’s identity provider and SPIRE; in production, both need operating, rotating and monitoring. Every read now makes policy calls. For scale: in zero-trust-rs, verifying a signed token takes about 15 microseconds, and a full hop through the gateway about 0.2 to 0.3 milliseconds, on a desktop machine. I have not measured the mesh’s policy calls, and you should measure your own. Signing keys for lineage need the same care as any other key, which in production means a key management service or Sigstore. Layered policy can sprawl, and computational policy cannot capture judgment; some decisions stay with a human, which is what grants are for.

What I built also has limits. The boundary reads fixture snapshots, not live Iceberg tables. The SPARQL servers still answer anyone on the internal network, because the stock image has no per-user query authentication; the boundary is their only route in from outside. And a grant’s purpose is a string the caller sends, recorded and checked against the grant but not against a register of allowed purposes. All of these are listed on the trust gaps page, with the demos.

Most of the value came from the unglamorous part: closing the doors. Authenticated storage, no published ports, a read-only query endpoint behind the boundary. If you do nothing else after reading this, find every way into your data products that does not pass through your policy.

Trust before policy

A policy is only as trustworthy as the identity it evaluates and the doors it guards. Federated governance gave the mesh a way to write rules once and apply them everywhere. Zero trust gives it the other half: proof of who is asking, through what, and about data from where, at every product’s boundary.

That raises a fair question. If trust is enforced at every product’s boundary, why keep a mesh at all, rather than one central platform that enforces it once? I will answer it in the fifth article. First, the consumer this series has been building toward: an AI agent, acting for a person, that reads and writes data products.

I would value pushback, especially from teams running policy as code in a mesh. Where does your policy’s identity come from, and how many ways into your data skip the policy entirely?
