Agents Need Write Gates, Not Just Read Grants

Reading on a person's behalf is becoming a product feature. Writing is where a data mesh has to prove the agent, check what it produced, and decide when a person must accept it.

By Narendra Loganathan • 20 min read • Updated 2026-11-24

A risk analyst asks an agent for help: find the high-risk customers whose risk scores have gone stale, and write a review note for each one.

After the previous article, the first half of that request was well governed in my reference data mesh. Every read passes one boundary per data product, which proves who the person is and which software is asking. The second half had nowhere to go. When I looked for the agent’s way to write a note, this is what I found:

write code                 RdfWriter.write_to_jena   <- POST to Fuseki's /update
Fuseki /update today       not served                <- the trust fix closed it
runtime callers            0                         <- dead code
write routes on boundary   none                      <- no governed way in

The read side proved who was asking. The write side did not exist.

The read side also had a quieter problem. The boundary checked a person and a workload. An agent acting for the analyst is a workload, so the boundary saw exactly what it saw for her own notebook: same person, same grant, same view of the data. Nothing recorded that an agent was involved, and nothing could give it less than its person had.

Reading on someone’s behalf is becoming a product feature

Credit first, because this has moved fast. Snowflake now supports OAuth token exchange (RFC 8693) for agents: a user’s token becomes a short-lived agent token, bounded by the user’s roles and a narrower scope, with the agent recorded in query history. AWS Bedrock AgentCore, Microsoft Entra’s on-behalf-of flow and the Azure SQL MCP server offer the same in their stacks. Starburst put the principle well in August: an agent “should not automatically inherit the full permissions of the person who started a conversation,” because “the difference is authority, not connectivity.”

That settles the easy part. Two things remain open.

First, the agent is often a claim. Snowflake’s documentation is candid that the actor in the exchanged token “is self-asserted and not verified by Snowflake.” The audit says an agent acted; nothing proved which software it was. That is my last article’s argument moved up a level: a policy is only as good as the identity it evaluates, including the identity of whatever acts for the person.

Second, writes. Almost everything published about agents and governed data is about reading; even Thoughtworks’ “State of data mesh in 2026” treats agents mainly as consumers. The question the first article in this series left open is still open: when an agent produces data, who owns it, what contract must it meet, and how do you undo it?

The audit: what my mesh knew about agents

I read the mesh again with an agent in mind and found five gaps, all in code I had already reviewed twice for other reasons.

An agent had no identity of its own. The boundary had no notion of delegation, so an agent was just another workload, and a forged claim about whom it acted for was ignored rather than refused.

An agent got its person’s whole view. Using the analyst’s grant, an agent could read everything she could, including KYC verdicts it had no reason to see.

There was no governed write path. The boundary was read-only, and the only write code targeted an endpoint that no longer existed.

Lineage could not name a delegator. Signed provenance recorded the producing workload, but not the person it acted for or what it read before it wrote.

The audit had no chain. It recorded a person and a workload, with no link from a write to the reads behind it.

The common cause: the mesh knew two kinds of participant, people and software, and an agent is a third.

How is an agent different from a microservice?

That claim invites the question I hear most often: isn’t an agent just another microservice? Both are software, with a workload identity, a certificate and a grant. Services have written sensitive data for years without a person approving each write, and nobody calls that a gap. So what changes?

Microservice Agent
Acts for itself a person, through a proven delegation
Decides at deploy time per request, at run time
Reviewed by a person once, in code review not before it acts
Access its own grant person ∩ its capability ∩ product
Cites what it read no yes, for every derived write
Who approves its writes policy, for every write policy, for captured and non-sensitive data; the domain’s owner, for its confidential conclusions; the person it describes, for personal values it derived

Two things. A service acts for itself; an agent acts with someone else’s authority. And a service’s decisions were made before it ran: its behavior was fixed when it was deployed, and a person reviewed it once, in code review. Every write afterwards carries out a decision someone already looked at. An agent decides per request, from whatever it read, and nobody reviewed that decision before it was made.

The whole fix follows from those two differences. Acting for someone means the delegation must be proven and the agent’s access cut below its person’s. Deciding at run time means the agent must cite what it read, and the few writes that carry its own judgment about something sensitive, a confidential conclusion or a personal value it derived, need a person to accept them at the write: the domain’s owner, or the person the data describes. Everywhere else, an agent should write as freely as a service.

The fix: an agent is a governed participant

As with the last two articles, I fixed this in the repository and kept the before beside the after. The old state is tagged agents-before, and six demos print both. The agents in those demos are scripted, not language models, and I explain why below.

Prove the actor, not just the person

The agent never holds a credential it could misuse. It runs beside a sidecar gateway, zero-trust-rs, the Rust gateway I built for my zero-trust work and have now made public. For each request, the agent hands its sidecar the analyst’s identity-provider token, and the sidecar mints a single-use token whose user is the analyst, exchanged for the boundary (RFC 8693) and bound to the agent’s own certificate. The boundary has its own sidecar, which verifies everything before the boundary sees the request:

GET /products/risk-compliance.risk-scores/rows   (through the boundary's sidecar)

TLS client certificate              <- sidecar: signed by the trusted CA
  spiffe://chakracommerce.com/ns/agents/sa/risk-review-agent
X-SPIFFE-OBO-Token: eyJhbGci...     <- sidecar: signature, trusted issuer,
                                       audience, expiry, single use
  user:  risk.analyst@chakra.fintech   (and her roles, from the IdP)
  actor: risk-review-agent          <- sidecar: actor must BE the mTLS peer
  cnf:   the agent's certificate    <- sidecar: bound to this certificate
                                    <- sidecar: capability policy,
                                       user AND agent
        ── loopback, same network namespace ──▶ boundary
                                    <- boundary: re-verifies the token,
                                       headers must agree with it
                                    <- OPA: person ∩ agent ∩ product

Each of those checks is a refusal the demos show. The agent’s token presented with the notebook’s certificate is refused (certificate_binding_mismatch). A token bound to the presenting certificate but naming a different actor is refused (obo_token_subject_mismatch). A replayed token is refused. A request with no client certificate stops at the TLS handshake. Delegation claims sent as plain headers to the boundary’s normal listener are ignored, then refused. The actor is recorded not because the agent said so, but because the connection, the certificate and a gateway’s signature agree.

The last hop, from the boundary’s sidecar to the boundary, is plain HTTP over loopback. That is safe because the two share a network namespace, so nothing else can reach that port. It is the usual service-mesh trust model, and the boundary still re-verifies the token rather than trusting the headers.

sequenceDiagram
    participant A as Analyst
    participant AG as Agent
    participant AZ as Agent sidecar
    participant BZ as Boundary sidecar
    participant B as Boundary
    A->>AG: task + IdP token (consent)
    AG->>AZ: mint for this request (loopback)
    AZ-->>AG: token: user=analyst, actor=agent, bound to agent cert, single use
    AG->>BZ: mTLS (agent cert) + token
    Note over BZ: signature, issuer, expiry, jti,<br/>actor = mTLS peer, binding,<br/>capability (user AND agent)
    BZ->>B: loopback: verified token + headers
    Note over B: re-verify token,<br/>person ∩ agent ∩ product,<br/>grant names the agent
    B-->>AG: rows (masked), audited with the chain

Delegation, proven at every hop. The agent’s token is minted per request for one analyst, bound to the agent’s certificate, and accepted only when the agent is the one actually connecting.

Give the agent less than its person

An agent’s effective access is the intersection of the person’s grant, the agent’s capability and the product’s policy. The grant names the agent’s workload, so the analyst’s notebook grant does not reach the agent. The owning domain names which agents may touch a product and which columns they may see. The platform’s guardrails still apply: a delegated read never returns personal data in the clear, and delegation chains are capped at two workloads.

analyst, her own notebook      read kyc_verdict              200
agent, for the analyst         read kyc_verdict              403
agent, using a notebook grant  read anything                 403
agent, with its own grant      read customer and risk band   200
agent, for the analyst         count customers by risk band  200
agent, for the analyst         count customers by fraud score 403

The last pair is a small design I like. An agent may be allowed to count by a column it cannot read row by row, which is often all it needs. Counts group only by public columns, because a group key reveals its value, and small groups are suppressed.

Who decided the data decides the human gate

My first version of the write path made every agent write a proposal for a domain owner to accept. That is safe, and wrong for most of a bank’s data.

Take a customer opening an account. She enters her name, address and Social Security number, through a form or an onboarding assistant. That is some of the most sensitive data the bank holds, yet no reviewer should sit between her and the record. She decided those values; whether a form service or an agent carries them, the software decided nothing. They are protected by encryption in motion and at rest and by masking on read, not by a queue.

The risk agent’s review note is different. Nobody supplied that text. The agent wrote it, at run time, from what it read. That is the unreviewed decision from the microservice comparison, and it is what a person should see before it becomes the bank’s record.

So the rule is neither “agents need approval” nor “sensitive data needs approval”. It is this: who decided the data decides whether a human gate applies. Each product’s contract declares whether it holds captured data, facts a person or a system of record supplied, or derived data, what a writer computed or judged from what it read. The platform’s guardrails combine that with the column classifications into write tiers, which a domain can tighten for its own products but never loosen:

What is written By a service By an agent
Captured, any classification, even personal direct direct, only for the person the record is about
Derived, public or internal direct direct, citing what it read
Derived, confidential or sensitive direct, if it is the product’s listed producer a proposal the domain’s owner accepts
Derived, personal direct, if it is the product’s listed producer a proposal the person it describes accepts; refused if it describes several people or no one

Direct does not mean ungated. A direct write passes the same checks as a proposal, each failing closed: verified identity and delegation, a write grant separate from read and propose grants, person ∩ agent ∩ product policy, the contract’s columns and key, the shared core’s SHACL shapes from article 2, and rate and size limits. An agent’s derived write must also cite the snapshots it used, and the boundary checks them against its own audit, so an agent cannot launder a conclusion by citing data it never read. A direct write skips only the queue: it becomes a new snapshot at once, signed with lineage whose accepted_by names the policy revisions that allowed it.

A new demo runs every row in one pass. The onboarding agent acts for a customer, the risk agent for the analyst, and the scores service for itself:

onboarding agent  captured  pii           direct, by policy
risk agent        derived   internal      direct, by policy
risk agent        derived   confidential  409 requires_owner_review
  as a proposal                           accepted by the owner
risk agent        derived   pii           422 agent_cannot_create_pii
scores service    derived   sensitive     direct, by policy

In the first line, the onboarding agent can write only its own customer’s record. The boundary derives her customer identifier from the token her identity provider signed, not from a field in the form, and refuses a record that names anyone else. Her personal values are then masked for anyone without a KYC grant.

The refused line is narrower than it looks. An agent never creates personal data on its own authority, but agents do derive personal values, and some are useful: a standardized postal address, for instance. When a derived value describes one person, that person decides, as the section after next shows. When it describes several people, or no one in particular, nobody can accept it, so it is refused whatever the domain’s policy says. An unclassified column counts as personal.

When an owner must accept

Where the gate applies, the agent writes a proposal instead, to the product of the domain that will own the result. Here that is the Risk team’s risk-compliance.risk-review-notes, whose note text is classified confidential. A proposal has its own grant, passes the same checks as a direct write, and then waits:

snapshot the agent read     75a06c247c6585dd...
high-risk, stale scores     2
proposal prop_a87fde1de9fd4021  pending
proposal prop_5f91fcf104e84843  pending
deprecated term             422        <- SHACL, from article 2
unminted customer id        422        <- the identity library, article 2
cites a snapshot never read 403        <- read-before-write lineage
agent accepts its own       403        <- only an owner, never a delegate
owner accepts               200

When the owner accepts, the boundary writes a new snapshot and signs a provenance statement for it, the format from article 3, now naming the delegation:

action          accept
on_behalf_of    risk.analyst@chakra.fintech
actor_chain     spiffe://chakracommerce.com/ns/agents/sa/risk-review-agent
derived_from    75a06c247c6585dd...
accepted_by     owner@risk-compliance.chakra.fintech

That record answers the question article 1 asked: what does the agent own when it produces data? Nothing. The agent proposed, the person authorized it, the inputs are named, and the domain owns the result because its owner accepted it. A direct write is no different: the domain accepted it in advance by writing the policy that allowed it, and the lineage names that policy. Either way the owner can roll a write back; the previous snapshot is restored, and the rollback is signed and audited. An agent can write and propose. It can never accept, reject or roll back, its own work included.

When the person it describes must accept

Some writes are not the owner’s to accept. When the onboarding agent turns the address a customer typed into its standardized postal form, the person who should decide is the customer, with the prompt a good form already shows: use this standardized address? The direct write returns 409 requires_subject_consent, and the agent submits a consent proposal instead, carrying both the value it would replace and the value it proposes:

onboarding agent, direct      409 requires_subject_consent
consent proposal              replaces  1 Analytical Way, London
                              proposed  1 ANALYTICAL WAY, LONDON
the agent, for her, accepts   403
the domain owner accepts      403
another customer accepts      403
the customer accepts          200  accepted_by  ada@customer.test
                                   consent      subject

Only she can accept or decline, with her own verified identity, checked against the record. The agent acting for her cannot bless what it proposed, and the domain owner cannot decide for her. Only an agent acting for her can propose a change to her record in the first place. Once she accepts, the value is captured data again, because she decided it, and the signed lineage says so. If she declines, or the proposal expires, her original value stays.

The human gate follows who decided the data. Captured facts and non-sensitive conclusions are written at once through the same automated gates any service passes. An agent’s confidential conclusions wait for the domain’s owner, a personal value it derives waits for the person it describes, and personal data about several people is refused.

No step remembers an approval

One rule runs through all of this: nothing relies on an approval being remembered. Every read, write, proposal and acceptance re-checks the grant and the delegation at that moment. Tokens are single use, so a crashed or retried agent cannot replay one, and a proposal submitted after its grant expired is refused even if the agent saw the grant earlier in the same run.

That is also my answer to a fair objection: why build all this when good models are already careful about scope? In my testing they mostly are. But an open, model-agnostic agent interface cannot know which model is on the other end, or how the next one will behave, so the governance has to be verifiable, auditable and reproducible by construction, whatever the agent is. That conclusion grew out of testing an idea from Jose Crespo’s recent piece in AI Advances on keeping meaning and permissions tied to their context. It deserves an article of its own, which I plan as a companion to article 2.

Why the agents in the demos are not language models

The risk agent reads the shared core’s version and the risk scores, picks the high-risk customers whose scores are more than 90 days old, proposes a note for each, and writes the day’s freshness summary. The onboarding agent submits one customer’s intake. Both do the same thing every time.

That is deliberate. The claim under test is the governance: the boundary refuses what an agent may not do, whichever way it decided. A language model would make the demos vary between runs without making the governance any stronger. It also keeps me honest. I have not built production LLM applications, and nothing here tests how a model decides. It tests that the platform does not have to trust how it decides.

What it costs

Delegation is not free. In zero-trust-rs, verifying a token takes about 15 microseconds, but minting one costs an RSA signature, roughly 0.4 to 1.4 milliseconds, once per request. On a desktop machine, a three-hop delegated round trip measured about 1 to 2.2 milliseconds, against 0.2 to 0.3 for an undelegated hop. That is fine for hundreds of requests per second per core, and worth measuring in your own stack.

The bigger cost is people, and the write tiers keep it small. Captured data and non-sensitive conclusions wait for no one. Only an agent’s confidential or sensitive conclusions wait for an owner, and a personal value it derives waits for the person it describes, a prompt customers already know from forms. A proposal nobody reviews expires, with nothing reaching the product in the meantime. That queue can still become the bottleneck, so size an agent’s confidential writes to what owners can actually review.

The repository has the limits I would expect a reviewer to find. The demos and tests use a stand-in that mints the gateway’s token shapes; the compose stack runs the real gateway as both sidecars. The analyst’s consent is simulated by handing the agent her token, bootstrap tokens stand in for SPIRE node attestation, and the signing keys are static files. Proposals, the read ledger, rate limits and the replay check live in one process. The tiers are only as good as the classifications: a confidential column labeled internal skips review, and a contract check can require a label but cannot judge it. No label can see personal data inside free text, either. And personal data relies on mTLS in motion, storage encryption at rest and masking on read; field-level encryption is left to the deployment. The repository’s list of residuals is on the agents page.

The agent is a participant, not a user

An agent is not a faster user, and it is not just another service. It is software acting with a person’s authority, and a data mesh has to treat it as a participant in its own right: a proven identity, a capability smaller than its person’s, a delegation recorded at every hop, and an owner for everything it produces. That owner accepts the agent’s work in advance, through policy, or at the write, when what is being recorded is the agent’s own judgment. And when the agent derived something about a person, that person decides.

The pieces were already in the mesh. The shared core and its shapes say what valid data means. The boundary proves who is asking and guards every door. Signed lineage says who produced what from what. An agent that writes is where they meet.

That leaves the question I promised to answer. If meaning, trust and agents are all enforced at each data product’s boundary, why keep a mesh at all, rather than one central platform that does it once? That is the next article, where the three threads become one architecture.

I would value pushback from teams putting agents in front of governed data. When your agent writes, who owns the result, and how would you undo it?
